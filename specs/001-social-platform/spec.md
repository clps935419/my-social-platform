## Clarifications

### Session 2026-01-30

- Q: refresh token 換發策略（rotation vs non-rotating）？ → A: Rotation（每次 refresh 都換發新的 refresh token，舊的立即失效）。
- Q: 圖片欄位（Post.image、User.coverImage）是 URL、Base64、或檔案上傳？ → A: URL 字串（僅允許 http/https），最大長度 2048；不做檔案上傳、不收 Base64。
- Q: 身分驗證是採 JWT Bearer 還是 Session Cookie？是否需要登出/換發/黑名單？ → A: JWT Bearer + refresh token；access token 驗證無狀態不存 DB；refresh token 存 DB（建議存雜湊）；不做 JWT 黑名單。
- Q: 列表分頁策略？ → A: `limit/offset`；`offset` 預設 0；`limit` 預設 20、上限 100；超限或不合法回應 400。
- Q: 時區策略？ → A: 後端時間一律以 UTC 儲存與輸出（ISO 8601、含 `Z`）。
- Q: 軟刪除貼文後留言策略？ → A: 不允許取得留言列表、也不允許新增留言；一律回應 404。
- Q: 手機號碼格式規範？ → A: 採 E.164；允許輸入含空白/破折號/括號，後端正規化後判斷唯一性；格式不符回應 400。
- Q: 風控/防爆破？ → A: 對 login（可含 register）做最小 rate limit；超過門檻回 429；訊息一般化避免枚舉。

### 決議摘要（對外契約以技術附錄為準）

- 圖片：URL（http/https）、最大長度 2048；不做上傳、不收 Base64。
- Auth：JWT Bearer + refresh token；refresh 採 rotation；不做 JWT 黑名單。
- 分頁：`limit/offset`；`offset` 預設 0；`limit` 預設 20、上限 100；不合法回 400。
- 時間：後端 UTC、ISO 8601（含 `Z`）。
- 軟刪除貼文：其留言列表/新增留言一律 404。
- 手機：E.164；允許輸入含空白/破折號/括號並正規化；格式不符 400。
- 風控：login（可含 register）最小 rate limit；超過回 429。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 訪客可瀏覽貼文與留言 (Priority: P1)

訪客（未登入）可以查看貼文列表（新到舊），並可查看任一貼文的留言列表；但不能發文、留言、編輯或刪除。

**Why this priority**: 提供最低門檻的內容瀏覽，支撐後續互動與成長。

**Independent Test**: 不需建立帳號即可用 API 取得貼文與留言，並確認受保護操作皆被拒絕。

**Acceptance Scenarios**:

1. **Given** 系統已有貼文與留言，**When** 訪客呼叫「列出貼文」與「取得貼文留言列表」，**Then** 取得資料且不包含已軟刪除貼文。
2. **Given** 訪客未登入，**When** 呼叫任何受保護 API（發文/留言/編輯/刪除），**Then** 依規則回應 401（未登入）或 403（權限不足）。

---

### User Story 2 - 使用手機號碼註冊與登入 (Priority: P1)

使用者可以使用手機號碼註冊帳號（手機號碼唯一且同時作為登入識別），並以手機號碼 + 密碼登入取得有效身分（用於後續受保護操作）。

**Why this priority**: 互動功能（發文、留言、管理貼文）都依賴可用的登入流程。

**Independent Test**: 以手機號碼完成註冊與登入，並用取得的身分呼叫受保護 API。

**Acceptance Scenarios**:

1. **Given** 手機號碼尚未被使用，**When** 使用者以手機號碼註冊，**Then** 註冊成功且系統保存使用者資料（不含明碼密碼）。
2. **Given** 手機號碼已存在，**When** 再次註冊同一手機號碼，**Then** 回應 409 並提供可理解的錯誤訊息。
3. **Given** 使用者以正確手機號碼與密碼登入，**When** 呼叫登入，**Then** 回傳可用於授權的憑證與使用者基本資訊。

---

### User Story 3 - 已登入使用者可發文並管理自己的貼文 (Priority: P2)

已登入使用者可以新增貼文、編輯自己的貼文、刪除自己的貼文（軟刪除）；非作者不得編輯或刪除他人的貼文。

**Why this priority**: 這是平台核心產出內容的能力。

**Independent Test**: 以兩個不同帳號建立貼文，驗證作者/非作者的編輯與刪除行為差異。

**Acceptance Scenarios**:

1. **Given** 使用者已登入，**When** 新增貼文，**Then** 系統回傳新貼文且可在貼文列表中（新到舊）看到。
2. **Given** 使用者是貼文作者且已登入，**When** 編輯貼文內容，**Then** 更新成功且更新後內容可被讀取。
3. **Given** 使用者不是貼文作者但已登入，**When** 嘗試編輯或刪除該貼文，**Then** 回應 403。
4. **Given** 作者已軟刪除貼文，**When** 訪客或一般使用者列出貼文，**Then** 列表不顯示該貼文。

---

### User Story 4 - 已登入使用者可對貼文留言，所有人可看留言列表 (Priority: P2)

已登入使用者可對任一貼文新增留言；訪客/登入者皆可取得留言列表供前端顯示。

**Why this priority**: 留言是最基本的互動，提升黏著與討論。

**Independent Test**: 對既有貼文新增留言並取得留言列表，驗證授權、資料完整性與排序。

**Acceptance Scenarios**:

1. **Given** 使用者已登入且貼文存在，**When** 對貼文新增留言，**Then** 留言建立成功且出現在留言列表。
2. **Given** 訪客未登入，**When** 嘗試新增留言，**Then** 回應 401。

### Edge Cases

- 手機號碼格式不合法、過短/過長、含非數字字元時的處理。
- 密碼不符合安全策略時的處理（例如長度不足）。
- 內容欄位為空白、過長、或包含疑似惡意腳本片段（XSS）時的處理。
- 操作不存在的貼文/留言（404）。
- 軟刪除貼文後：是否仍允許取得其留言列表、是否允許新增留言。
- 未登入呼叫受保護 API（401）與已登入但無權限（403）的差異回應。

## Requirements *(mandatory)*

### Functional Requirements

#### 身分與權限

- **FR-001 註冊**：系統 MUST 允許使用者以「手機號碼」註冊帳號，且手機號碼 MUST 唯一。
  - 驗收：同一手機號碼重複註冊回應 409；成功註冊回應 201 並回傳使用者基本資料。

- **FR-002 登入**：系統 MUST 允許使用者以手機號碼作為登入識別進行登入驗證。
  - 驗收：正確憑證登入成功並回傳授權憑證；錯誤憑證回應 401。

- **FR-003 受保護 API**：系統 MUST 對「新增貼文、編輯貼文、刪除貼文、新增留言」等互動功能要求登入。
  - 驗收：未登入呼叫上述 API 回應 401。

- **FR-004 作者權限**：系統 MUST 僅允許貼文作者編輯或刪除自己的貼文。
  - 驗收：非作者嘗試編輯/刪除回應 403。

#### 貼文

- **FR-005 新增貼文**：已登入使用者 MUST 能新增貼文，貼文包含文字內容，並可選擇性包含圖片欄位。
  - 驗收：新增成功回應 201，回傳貼文識別與建立時間；貼文可在列表中被讀取。

- **FR-006 列出貼文**：系統 MUST 提供「列出所有貼文」能力，至少支援新到舊排序，且列表 MUST 排除已軟刪除貼文。
  - 驗收：軟刪除貼文後，列表不再出現該貼文。

- **FR-007 編輯貼文**：貼文作者 MUST 能更新自己的貼文內容（與可選圖片欄位）。
  - 驗收：作者更新成功回應 200 並回傳更新後貼文；非作者 403。

- **FR-008 軟刪除貼文**：貼文作者 MUST 能刪除自己的貼文，且刪除 MUST 為軟刪除（一般列表不顯示）。
  - 驗收：刪除成功回應 204；一般列表不顯示；再刪除同一貼文的行為需有一致且可預期回應（例如 404 或 204）。

#### 留言

- **FR-009 新增留言**：已登入使用者 MUST 能對任一存在的貼文新增留言。
  - 驗收：新增成功回應 201 並回傳留言內容與建立時間；未登入 401。

- **FR-010 取得留言列表**：系統 MUST 提供「取得貼文留言列表」供前端顯示。
  - 驗收：回傳留言列表，並至少提供由舊到新或新到舊其中一種一致排序（需在 API 契約中定義）。

#### 對外介面與文件

- **FR-011 對外介面**：系統 MUST 提供可被前端使用的對外介面，以支援註冊、登入、貼文、留言等行為。
  - 驗收：前端可透過對外介面完成 4 個主要使用者旅程（註冊/登入、瀏覽、發文管理、留言）。

- **FR-012 介面文件**：系統 MUST 提供可用的介面文件（含可互動測試的文件頁面），且路徑固定並可在部署環境存取。
  - 驗收：在部署後可存取文件頁面並可執行試呼叫。

### Non-Functional Requirements

- **NFR-001 安全 - 密碼保護**：系統 MUST 以 salt+hash 儲存密碼，不得以明碼或可逆形式儲存。
  - 驗收：資料庫中無明碼密碼；登入流程僅以雜湊比對。

- **NFR-002 安全 - 注入防護**：系統 MUST 防止 SQL Injection 與同等級輸入注入攻擊。
  - 驗收：以安全測試字串驗證不可繞過驗證或破壞資料完整性；具體技術限制詳見技術附錄。

- **NFR-003 安全 - XSS 防護**：系統 MUST 防止使用者輸入在前端被當作可執行腳本呈現。
  - 驗收：貼文/留言/簡介顯示時不得執行腳本；前端/後端需有一致策略（例如輸出編碼或白名單）。

- **NFR-004 錯誤資訊保護**：對外錯誤回應 MUST 不洩漏 SQL、堆疊、內部路徑或敏感資訊。
  - 驗收：任何 4xx/5xx 回應皆為一般化訊息與錯誤代碼。

- **NFR-005 架構與部署**：系統 MUST 支援三層式架構（Web Server / Application Server / Database），且 MUST 可用單一指令一鍵啟動。
  - 驗收：啟動後靜態站點可被存取，且 Web Server 會將對外介面請求轉送至 Application Server；細則詳見技術附錄。

- **NFR-006 介面文件可用**：系統 MUST 提供介面文件且可在部署環境以固定路徑存取。
  - 驗收：文件頁面可存取並可試呼叫對外介面。

- **NFR-007 交易一致性**：當一次操作涉及多筆或多表異動時，系統 MUST 確保原子性（任一步驟失敗需回滾）。
  - 驗收：刻意製造其中一步失敗，最終資料狀態不得部分寫入。

### Key Entities *(include if feature involves data)*

- **User**：代表平台使用者。
  - 核心屬性：userId、phoneNumber（唯一且作為登入識別）、userName、email（選填）、passwordHash、passwordSalt、coverImage（選填）、biography（選填）、createdAt、updatedAt。

- **Post**：代表使用者發佈的貼文。
  - 核心屬性：postId、userId（作者）、content、image（選填）、createdAt、updatedAt、deletedAt（或等價的軟刪除欄位）。
  - 關係：一個 User 可有多個 Post。

- **Comment**：代表對貼文的留言。
  - 核心屬性：commentId、postId、userId（留言者）、content、createdAt。
  - 關係：一個 Post 可有多個 Comment；一個 User 可有多個 Comment。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001 註冊可用性**：新使用者可在 2 分鐘內完成註冊與登入，並成功取得可用的授權身分。
- **SC-002 權限正確性**：未登入互動操作的拒絕率為 100%（皆回應 401）；非作者編輯/刪除的拒絕率為 100%（皆回應 403）。
- **SC-003 內容可用性**：貼文與留言的新增後可在 3 秒內於列表中被看到（以一般網路環境測試）。
- **SC-004 一鍵啟動**：在全新環境中以單一指令啟動後，使用者可在 5 分鐘內完成：瀏覽前端、取得貼文列表、開啟介面文件頁面。

### 驗收條件（對應整體需求）

以下驗收以黑箱方式驗證，作為交付門檻：

1. 註冊：手機號碼唯一；成功註冊回傳 userId；重複註冊 409。
2. 登入：正確憑證成功、錯誤 401；登入後可呼叫受保護 API。
3. 權限：訪客可讀貼文/留言；訪客不可發文/留言；非作者不可編輯/刪除（403）。
4. 貼文：新增、列表新到舊、作者可編輯、作者可軟刪除；軟刪除後列表不顯示。
5. 留言：登入可新增；所有人可取得留言列表。
6. 資料存取約束：資料存取遵循既定資料層約束與安全規範（細則詳技術附錄）。
7. 資料一致性：跨多步驟異動失敗時必須回到一致狀態（不可部分成功；細則詳技術附錄）。
8. 安全：密碼不得明碼；防 SQL Injection 與 XSS；對外錯誤不洩漏堆疊/SQL。
9. 部署：可一鍵啟動三層服務；對外介面可被存取；介面文件頁面固定路徑可用（細則詳技術附錄）。

（註）第 6～9 點之技術細則與可驗收項目彙整於 `appendix-technical-contract.md`，以避免本規格混入過多實作細節。
